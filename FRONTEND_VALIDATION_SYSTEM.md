# Frontend Data Accuracy & Rate Limit Protection System

## Problem Solved

**Issue**: The frontend was showing an AAPL signal despite an empty database because the `/api/signals` endpoint was generating signals in real-time on every request. This caused:
1. Confusing user experience (signals appeared when database was empty)
2. **Rate limit abuse** - Every frontend page load triggered external API calls to Tiingo/Alpha Vantage
3. Potential API quota exhaustion during high traffic

**Solution**: Implemented a multi-layered approach:
1. Modified signals endpoint to read from database instead of computing in real-time
2. Enhanced bot to store technical indicators (SMA20, SMA50, RSI) with signals
3. Added 15-minute freshness filter to only show recent signals
4. Created multi-agent test suite to validate rate limit compliance

## Changes Made

### 1. Database Schema Enhancement
**File**: Supabase database migration
```sql
ALTER TABLE signals
ADD COLUMN IF NOT EXISTS sma_20 NUMERIC,
ADD COLUMN IF NOT EXISTS sma_50 NUMERIC,
ADD COLUMN IF NOT EXISTS rsi NUMERIC CHECK (rsi >= 0 AND rsi <= 100);
```

### 2. Bot Signal Storage
**File**: `backend/app/main.py:89-114`

The trading bot now stores technical indicators with every signal:
- SMA20, SMA50, RSI values
- Signal type (buy/sell/hold)
- Current price
- Signal strength

### 3. API Endpoint Refactoring
**File**: `backend/app/api/endpoints/signals.py:34-128`

**Before** (Rate Limit Abuse):
```python
# Old code - called external APIs on every request
for symbol in symbols:
    ohlcv_data = fetch_ohlcv(symbol)  # External API call!
    signals = generate_signals(ohlcv_data)
```

**After** (Rate Limit Safe):
```python
# New code - reads from database only
response = supabase.table("signals") \
    .select("*") \
    .gte("created_at", fifteen_min_ago) \  # Freshness filter
    .execute()
```

**Impact**: ✅ **ZERO external API calls from frontend requests**

### 4. Frontend Clarity
**File**: `frontend/components/SignalsPanel.js:219-230`

Added clear explanation that signals come from the database and are generated by the bot during market hours.

### 5. Validation Framework
**File**: `backend/tests/agents/`

Created multi-agent test suite:
- **Rate Limit Compliance Agent** (12 tests) - Validates cache effectiveness, concurrent request handling
- **Signal Storage Agent** (8 tests) - Validates signal persistence and retrieval

## Rate Limit Protection Features

### Current Protection Mechanisms

1. **5-Minute Cache** (Daily Data)
   - `backend/app/services/fetcher.py:35`
   - Caches OHLCV data for 5 minutes
   - Hit rate > 95% under normal load

2. **1-Minute Cache** (Intraday Data)
   - `backend/app/services/fetcher.py:37`
   - Faster refresh for intraday bars

3. **24-Hour Fallback Cache**
   - `backend/app/services/fetcher.py:36`
   - Emergency cache when all APIs fail

4. **API Key Rotation**
   - Supports up to 5 Alpha Vantage keys
   - Automatic failover on rate limit errors

5. **Database-Backed Signals** ⭐ **NEW**
   - Signals endpoint reads from database
   - NO external API calls from frontend

### Rate Limit Metrics

| Metric | Target | Status |
|--------|--------|--------|
| Cache Hit Rate | > 95% | ✅ Validated by tests |
| External API Calls (Signals Endpoint) | 0 | ✅ Zero calls |
| Concurrent Request Deduplication | < 3 API calls for 5 concurrent requests | ✅ Tested |
| Fallback Cache Activation | On all API failures | ✅ Tested |

## Troubleshooting

### No Signals Appearing

**Possible Causes**:
1. Bot hasn't run yet (check bot logs)
2. Markets are closed (bot sleeps when closed)
3. All signals > 15 minutes old (freshness filter)

**Debug**:
```sql
-- Check signals in database
SELECT * FROM signals ORDER BY created_at DESC LIMIT 10;

-- Check bot last run time
SELECT * FROM equity ORDER BY timestamp DESC LIMIT 1;
```

### Rate Limit Errors

**If you see rate limit errors**:
1. Check cache effectiveness tests
2. Verify signals endpoint not calling `fetch_ohlcv()`
3. Add additional Alpha Vantage API keys (ALPHA_VANTAGE_API_KEY_2, etc.)
4. Increase cache TTL temporarily
